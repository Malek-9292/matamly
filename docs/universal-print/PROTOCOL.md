# Matamly Universal Print Protocol

Version: 1.0 (initial transport contract)

## Transport

Agents make outbound HTTPS requests only. The server does not open inbound connections to a cashier device, and the browser does not connect to a local printer. This avoids fixed device IPs and mixed-content access from an HTTPS cashier page.

The first transport is authenticated HTTPS long-polling. It is deliberately used instead of requiring a persistent WebSocket: Android background execution and Render instance restarts make a reconnectable pull channel simpler to recover. A future WSS transport can carry the same JSON envelopes without changing the job model.

## Device identity and credentials

- Each installation has a UUID device ID.
- Device credentials are generated by the server during admin pairing and shown once.
- Only a SHA-256 hash of the credential is stored in the database.
- Requests use `Authorization: Bearer <device-token>`.
- Revoking a device invalidates its credential immediately.
- Device tokens are not browser-visible and must never be placed in public JavaScript or checked into source control.

## Agent endpoints

All endpoints are HTTPS and return JSON.

- `POST /api/print/v1/devices/pair` — admin-only registration/pairing.
- `POST /api/print/v1/devices/heartbeat` — device status, version and capabilities.
- `GET /api/print/v1/jobs/claim?wait=20` — claim one eligible job; returns `{ job: null }` when none is available.
- `POST /api/print/v1/jobs/:id/stage` — report accepted-by-agent, submitted-to-spooler, printer-acknowledged, paper-confirmed or failure stage.
- `POST /api/print/v1/jobs/:id/result` — final agent result; success must name the strongest confirmed stage.
- `POST /api/print/v1/devices/revoke` — admin-only revocation.

The exact route implementation is introduced incrementally. Until an endpoint exists in the server, agents must not assume it is available.

## Job envelope

```json
{
  "protocolVersion": 1,
  "jobId": 123,
  "idempotencyKey": "order-456-auto",
  "createdAt": "2026-11-18T18:00:00.000Z",
  "document": {
    "encoding": "utf-8",
    "contentType": "text/plain",
    "receiptText": "..."
  },
  "printer": {
    "printerId": "uuid",
    "connectionType": "usb",
    "commandSet": "escpos"
  }
}
```

## Delivery and acknowledgement semantics

- A database lease prevents two agents from claiming the same job concurrently.
- Agents persist claimed job IDs locally before sending bytes to the printer.
- The same job ID must not be printed twice by an agent unless an explicit manual reprint creates a new job.
- Network receipt is not print success.
- `submitted_to_spooler` means the OS accepted the print command; it does not prove paper was produced.
- `printer_acknowledged` means a printer status response was received where supported.
- `paper_confirmed` is only valid when the hardware actually exposes a trustworthy paper/print completion signal.
- If power/network fails after bytes may have reached the printer but before the acknowledgement is stored, the job is marked uncertain and requires policy-based reconciliation rather than blind replay.

## Platform adapters

Adapters implement the same job and acknowledgement contract:
- Android: USB Host API + ESC/POS; Epson TM-T20II is the first target.
- Windows: Windows spooler / installed driver or supported raw USB adapter.
- macOS/Linux: CUPS/IPP or a supported ESC/POS transport.

A platform is not considered supported until its adapter is built and tested on real hardware.
